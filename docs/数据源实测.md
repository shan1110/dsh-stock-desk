## 2. 稳定性实测

复现：`node tools/test-reliability.mjs 15`

| 接口 | 成功率 | 平均耗时 | 最慢 | 失败模式 |
|---|---|---|---|---|
| 腾讯 批量报价(50 只) | 15/15 | 60 ms | 244 ms | — |
| 东财 日 K | 15/15 | 255 ms | 343 ms | — |
| 东财 行业板块榜 | **14/15** | 215 ms | 282 ms | `UND_ERR_SOCKET` ×1 |
| 同花顺 涨停概览 | 15/15 | 95 ms | 289 ms | — |

**结论：东财 `clist` 单次失败率约 7%，且失败是「连接被对端直接关闭」而非超时。**
`lib/eastmoney.js` 因此走 `withRetry`（默认 3 次尝试 + 指数退避），剩余失败率量级 10⁻³。
样本量 15，只能作为量级参考，不足以给出精确失败率。

## 4. 已确认的字段陷阱

### 4.1 东财 K 线缺 `beg`/`end` 会静默返回空

```
GET …/stock/kline/get?secid=1.600519&…&klt=101&fqt=1          → HTTP 200, {rc:102, data:null}
GET …/stock/kline/get?secid=1.600519&…&klt=101&fqt=1&beg=…&end=… → HTTP 200, {rc:0, data:{…}}
```

**是 HTTP 200 + `data:null`，不是报错。** 不检查 `rc` 会拿到空数组而不自知。
`lib/eastmoney.js` 的 `fetchKline` 强制填 `beg`/`end`，并在 `rc !== 0` 时抛错。

### 4.2 字段号不能跨接口复用

`f104`/`f105` 在 `clist/get` 里是板块内**上涨/下跌家数**，
在 `stock/get` 里是**财务项**。
`f62` 在 `stock/get` 里返回 2。字段号只在声明它的那个接口里有意义。

### 4.3 同花顺 `block_top` 的 `change` 字段语义不明 —— 不展示

`block_top` 单条的全部字段：

```
code, name, change, limit_up_num, continuous_plate_num, high, high_num, days, stock_list
```

`change` 实测值：机器人概念 `0.0501`、新能源汽车 `-0.1227`、华为概念 `-0.1661`、比亚迪概念 `-0.1016`。

试过两种解读，都不成立：

| 板块 | `change` 原值 | 若已是百分数 | 若为小数比例 |
|---|---|---|---|
| 机器人概念 | `0.0501` | +0.05% | +5.01% |
| 新能源汽车 | `-0.1227` | -0.12% | **-12.27%** |

- 上表同期这四个板块的成分股**全部涨停**（+10% ~ +20%），板块不可能跌到 -12%。
- A 股板块单日涨跌幅有 ±10%~±20% 的上限，-12.27% 本身就是不可能的取值。
- 符号方向也和成分股相反。

反例说明：`stock_list` 是**该板块当日涨停的个股**，不是全部成分股。
第一版探测脚本拿它当「板块整体涨跌幅」的代理，属于循环论证，结论无效——该脚本的方法已作废。

**处置：`lib/ths.js` 不输出 `changePct`。** 板块涨跌幅改用语义已验证的东财 `clist` 的 `f3`。
东财侧验证：行业「其他数字媒体 +13.01%、涨跌家数 2/0」——该行业只有 2 只成分股且都涨，
+13% 与「少数成分股同时大涨」自洽，故 `f3` 是真实百分数。

## 5. 请求量核算

盘中一轮刷新（自选 10 只 + 三大指数 + 全市场扫描 + 情绪 + 板块）：

| 请求 | 次数 |
|---|---|
| 腾讯 自选+指数 | 1 |
| 腾讯 全市场扫描（5549 只，200/批） | 7 |
| 同花顺 涨停概览 | 1 |
| 同花顺 连板梯队 + 板块榜 | 2 |
| 东财 板块榜 | 2 |
| **合计** | **约 13** |

全市场扫描 7 个请求实测约 2.9 s，且只在情绪/涨跌家数需要时才发起。
非交易时段轮询间隔放宽到 60 s。
